### 1.2 外部工具链（引擎B）

| 工具 | 获取方式 | 所属里程碑 |

#### 1.2.1 lcgamboa/qemu fork 在 Windows 上的构建（MSYS2）

> 仅当 M5 决定走 lcgamboa fork 自行构建时执行；优先评估 Velxio 预编译包或 Espressif fork 是否已满足 GPIO 导出需求，能不复用源码构建就跳过本节。

依赖：MSYS2（pacman）+ mingw-w64 工具链。整个流程在 `D:\qemu-build` 根目录（路径不含空格）下、mingw64 shell 中执行：

```bash
# 1. 安装 MSYS2 后，在 mingw64 shell 中安装依赖
pacman -S --needed mingw-w64-x86_64-{gcc,make,ninja,pkg-config,python} git

# 2. 克隆 lcgamboa fork 并切到 picsimlab-esp32 分支
git clone https://github.com/lcgamboa/qemu.git
cd qemu && git checkout picsimlab-esp32

# 3. 配置（仅构建 xtensa softmmu，目标机器 esp32）
./configure --target-list=xtensa-softmmu --enable-slirp --disable-tools --disable-docs

# 4. 编译（Ninja 并行）
ninja -C build

# 5. 产物 build/qemu-system-xtensa.exe，移动到 config/app.json 的 tools.qemuXtensa 路径
```

常见问题：`slirp` 缺失时去掉 `--enable-slirp`（仅影响 WiFi 网络后端，一期 WiFi 走语义模拟可忽略）；configure 阶段若报 `python not found`，确认 `mingw-w64-x86_64-python` 已装；产物运行时缺 DLL，把 `msys2/mingw64/bin` 加入 PATH 或拷贝所需 DLL 到产物目录。

### 1.4 可观测性与监控

| 维度 | 实现 | 暴露方式 |
|---|---|---|
| 后端健康 | `/api/health` 返回进程 uptime/db 连接/工具链状态 | REST |
| 工具链状态 | `/api/health/tools`（§1.3） | REST |
| QEMU 异常发现 | QemuManager 监听子进程 `exit` 事件，非零退出立即转 `state=error` 并把退出码+stderr 尾 2KB 推 WS `log.error` | WS + REST `GET /api/sessions/:id` |
| 编译任务指标 | builds 表记录 status/started_at/finished_at；`GET /api/builds?status=running` 仪表板 | REST |
| WS 会话指标 | 在线会话数、各会话状态、最近事件计数；`GET /api/metrics/sessions` | REST（不暴露 Prometheus，单机定位） |
| 结构化日志 | pino，JSON 行式输出到 `logs/server.log` + stdout，按级别/info+warn+error 分文件轮转 10MB×5 | 文件 |
| 前端错误 | window.onerror/promise rejection → POST `/api/ingest/frontend-error`（限频 1 条/10s） | REST |

> 不引入 Prometheus/Grafana：单机定位，REST 仪表板 + 文件日志足够；P3 评估是否升级。

## 3. 测试与验收总纲（各里程碑共同遵循）

### 3.1 测试分层

| 层级 | 工具 | 执行时机 |
|---|---|---|
| L1 单元 | vitest | 每次提交（pre-commit + CI） |
| L2 组件 | vitest + @testing-library/react | 每次提交 |
| L3 API/WS 集成 | vitest + fastify.inject | 每次提交 |
| L4 E2E | Playwright（Chromium） | 里程碑验收前 |
| L5 Golden 仿真一致性 | 自研运行器（M4 起建） | 里程碑验收前 |

#### 3.1.1 CI 平台与流水线

**平台**：GitHub Actions（开源仓库免费额度足够；不引入 Jenkins/CircleCI）。仓库托管在 GitHub，PR 与 push 触发 CI。

**两条流水线**：

| 流水线 | 触发 | Job | 失败处理 |
|---|---|---|---|
| `ci.yml`（PR/push） | `pull_request`、`push: branches:[main]` | ① `lint`：`pnpm lint`（eslint + prettier --check）<br>② `typecheck`：`pnpm typecheck`（全包 tsc --noEmit）<br>③ `test`：`pnpm test`（vitest run，跨 apps 与 packages） | 任一失败阻塞 merge |
| `e2e.yml`（里程碑验收前手动 dispatch） | `workflow_dispatch` | ④ `e2e`：`pnpm e2e`（Playwright Chromium，安装浏览器缓存）<br>⑤ `golden`（M4 起）：`pnpm golden`（运行器加载 examples 双引擎跑一遍） | 里程碑验收前必跑 |

配置要点：
- 使用 `pnpm/action-setup@v4` 与 `actions/setup-node@v4`（`cache: pnpm`）；
- Playwright 用 `browser-actions/setup-playwright@v1` 缓存，避免每次下载；
- `packages/shared` 改动时全量跑（`paths-filter`）；其余改动只跑受影响包的 test job（`pnpm --filter ... test`）。

### 3.2 Golden 测试机制（L5）

每个示例工程附 `golden.json` 剧本（输入序列 + 预期 GPIO 事件 + 预期串口输出 + OLED 帧哈希），运行器加载工程→指定引擎执行→比对。容差：时间 ±100ms；OLED 帧逐像素容差 ≤1%。示例见 M4。

Golden CLI（`pnpm golden [--example <id>] [--engine both|qemu-remote|micropython-wasm]`）：任一用例 fail → 退出码 1（CI 阻塞）；全部用例无条件断言（M6 期间曾按跳过表 `ENGINEA_KNOWN_LIMITS` 豁免 button-led 引擎A 用例，已随 wasm 重建删除——P1 整改项闭环，见《06-边界说明》§3）。

### 3.3 缺陷分级与里程碑准出

| 级别 | 定义 | 处理 |
|---|---|---|
| S1 | 崩溃/数据丢失/安全漏洞 | 阻塞里程碑 |
| S2 | 主流程不可用 | 阻塞里程碑 |
| S3 | 次要缺陷 | 遗留 ≤3 且登记 issue |
| S4 | 体验优化 | backlog |

### 3.4 通用准出条件（每个里程碑）

1. `pnpm lint` / `pnpm typecheck` 全绿；
2. 该里程碑"测试与验收"小节全部条目通过；
3. WS/REST 协议如有变更，`packages/shared` 同步更新并评审。

### 3.6 Git 工作流

**分支策略**：简化版 GitHub Flow（不引入 Git Flow 的 develop/release 分支，单机定位足够）。

> **单人期修订（2026-08-28）**：当前为单人开发，`main` 不设分支保护，允许直推；
> 直推前须本地 lint + typecheck + test 全绿（CI push 触发复核，红即修）。
> Conventional Commits 照常执行，保证 changelog 与 tag 自动生成可用。
> 转多人协作或引入大改动/实验性改动时，恢复下表的 PR 流程与分支命名。

| 分支 | 用途 | 命名 |
|---|---|---|
| `main` | 可发布主干（单人期允许直推，多人期受保护只接 PR） | `main` |
| 功能分支 | 单个里程碑子任务开发（大改动/实验性改动） | `feat/<scope>-<topic>` 如 `feat/m2-wiring-anchor` |
| 修复分支 | 缺陷修复（影响面大时使用） | `fix/<topic>` 如 `fix/pinbus-conflict-false` |
| 示例/文档 | 不影响代码 | `docs/<topic>` / `chore/<topic>` |

**PR 规则（多人期 / 大改动）**：
- 必须经 §3.1.1 `ci.yml` 三 Job 全绿才可 merge；
- 至少 1 个 Reviewer approve（自研项目可自批，但 PR 描述必须填"实现范围/测试项/验收点"三要素对照对应里程碑）；
- Squash merge，commit message 用 [Conventional Commits](https://www.conventionalcommits.org/)（`feat:`/`fix:`/`docs:`/`refactor:`/`test:`/`chore:`）；
- 关联 issue 在 PR 描述中 link。

### 3.7 日志规范（前后端统一）

> 配合 §1.4 可观测性，统一前后端日志格式，便于关联排查。

**后端（pino）**：JSON 行式，每行含字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `time` | ISO8601 | pino 自动 |
| `level` | 'trace'\|'debug'\|'info'\|'warn'\|'error'\|'fatal' | 数字+字符串双写 |
| `msg` | string | 事件摘要 |
| `module` | string | 固定枚举：`build`\|`qemu`\|`ws`\|`db`\|`rest`\|`app` |
| `reqId`/`sessionId`/`buildId` | string | 链路追踪上下文（按场景选填） |
| `err` | object | error 时附 `{name,message,stack,code}` |

输出：stdout（开发期）+ `logs/server.log`（info+）+ `logs/server.error.log`（error+），轮转 10MB×5 份（pino-roll）。

**前端（console + 上报）**：
- 开发期：`console.warn/error` 走 pino-browser（同一 pino 实例，传输到 stdout via Vite overlay）；
- 生产期：捕获 `window.onerror` 与未处理 `unhandledrejection`，限频 POST `/api/ingest/frontend-error`，payload = `{msg, stack, url, line, col, ua, sessionId?, buildId?}`。

**级别约定**：
- `error`：阻塞主流程、需用户感知（引擎崩溃、编译失败、WS 断线）；
- `warn`：可降级继续（多驱动冲突、工具链缺失、路径穿越被拒）；
- `info`：关键节点（会话起停、编译起止、保存工程）；
- `debug`：仅开发期（PinBus 事件流、WS 消息原文）——生产构建剔除。

### 3.8 后端中间件链注册顺序（N14）

Fastify 插件按以下顺序在 `apps/server/src/index.ts` 注册，顺序错位会导致日志缺失、校验绕过或错误泄漏：

| 顺序 | 插件 | 作用 | 关键点 |
|---|---|---|---|
| 1 | `@fastify/cors` | 跨域 | 仅允许 `apps/web` dev origin（生产同源则 `origin: false`），不开放 `*` |
| 2 | pino logger（内置） | 请求日志 | `serializers` 屏蔽敏感字段；`level` 从 config 读，`request` 日志含 `reqId` |
| 3 | `requestId` 上下文 | 链路追踪 | 与 pino `reqId` 联动，所有日志自动带 `reqId` |
| 4 | `@fastify/rate-limit`（仅 WS 入口/编译提交路由） | 限频 | 全局默认 `max: 100/30s`；`POST /api/builds` 单独 `max: 5/30s`；`/api/ingest/frontend-error` `max: 1/10s`（§1.4 限频对齐） |
| 5 | 全局 `setErrorHandler` | 错误兜底 | 统一响应 `{ error: { code, message, traceId } }`，500 不泄漏 stack，log.error 记录原始 stack；**必须先于路由注册**（fastify 4 子上下文在 register 时捕获 handler） |
| 6 | `setNotFoundHandler` | 404 兜底 | 未命中路由返回 404 JSON，不暴露路由表；同样先于路由注册 |
| 7 | 路由注册（REST） | 业务路由 | `/api/health`、`/api/parts`、`/api/boards`、`/api/projects`、`/api/builds`、`/api/sessions/:id` 等 |
| 8 | `@fastify/websocket` | WS 网关 | 注册顺序在 REST 后，确保 `/ws` 不被 rate-limit 全局规则误伤；WS 连接 `preValidation` 鉴权（单机无 token，仅校验 `sessionId` 存在） |
| 9 | `@fastify/static`（生产形态，§8.1） | 托管前端 | 仅 web 产物存在时注册，dev 由 Vite 代理 |

**注册顺序约束**：
- CORS 必须第 1，否则后续插件的预检请求被拒；
- pino 必须在所有业务插件之前，否则请求日志缺失；
- rate-limit 必须在路由注册之前，否则部分路由绕过限频；
- **errorHandler / setNotFoundHandler 必须在路由注册之前**：fastify 4 子上下文（`fastify.register` 的插件）在注册时从父上下文捕获 error/notFound handler，后置设置不会作用于已注册路由——业务抛错会落回 Fastify 默认错误体 `{ statusCode, error, message }`，违反 01-§5.2.1 envelope 约定（M3 回归教训）；
- `@fastify/static` 必须最后注册，否则 catch-all 路由会吞掉 API 请求。

**示例（apps/server/src/index.ts 节选）**：

```ts
import Fastify from 'fastify';
import cors from '@fastify/cors';
import rateLimit from '@fastify/rate-limit';
import websocket from '@fastify/websocket';
import staticPlugin from '@fastify/static';
import { restRoutes } from './routes/index.js';
import { wsGateway } from './ws/gateway.js';
import { config } from './config.js';

const app = Fastify({
  logger: { level: config.logLevel, serializers: { /* ... */ } },
  genReqId: () => crypto.randomUUID(),
});

await app.register(cors, { origin: config.corsOrigins });
await app.register(rateLimit, { max: 100, timeWindow: '30s' });

// errorHandler / notFound 必须在路由 register 之前设置（fastify 4 封装语义，见上方约束）
app.setErrorHandler((err, req, reply) => {
  if (err.statusCode && err.statusCode < 500) {
    // 4xx：业务错误码透传（HttpError），框架错误归一 BAD_REQUEST
    reply.code(err.statusCode).send({ error: { code: err.code ?? 'BAD_REQUEST', message: err.message, traceId: req.id } });
    return;
  }
  req.log.error({ err }, 'unhandled error');
  reply.code(500).send({ error: { code: 'INTERNAL', message: 'Internal Server Error', traceId: req.id } });
});
app.setNotFoundHandler((req, reply) => {
  reply.code(404).send({ error: { code: 'NOT_FOUND', message: `Route ${req.method} ${req.url} not found`, traceId: req.id } });
});

await app.register(restRoutes);              // 7
await app.register(websocket);               // 8
await app.register(wsGateway, { prefix: '/ws' });

if (config.env === 'production') {
  await app.register(staticPlugin, { root: path.resolve('apps/web/dist') });
}

await app.listen({ port: config.port, host: '0.0.0.0' });
```

> 注意：Fastify 插件系统对注册顺序敏感（encapsulation），上述 `await` 串行确保每个插件就绪后再注册下一个；`setErrorHandler` / `setNotFoundHandler` 是实例方法（非插件），但 fastify 4 的子上下文在 `register` 时即从父上下文捕获这两个 handler，因此必须在首个路由插件注册**之前**调用（M3 回归教训：后置设置导致业务错误返回 Fastify 默认错误体而非 envelope）。

### 3.9 前端 React ErrorBoundary 约定（N16）

前端在关键子树包裹 React ErrorBoundary，避免单个面板崩溃带倒整个工作台。约定如下：

**布局层级与 Boundary 划分**：

| Boundary 位置 | 覆盖范围 | Fallback UI | Reset 策略 |
|---|---|---|---|
| `AppRoot` | 整个应用 | 全屏错误页（含"重载"按钮 + 复制错误堆栈） | `location.reload()` |
| `CanvasBoundary`（电路画布区） | react-konva 画布 + 引脚热区 | 画布占位卡片 + "重试"按钮（保留 circuitStore 状态，仅重渲染） | 重置 `<Stage key={retryKey}>` 的 key 触发重挂 |
| `EditorBoundary`（Monaco 区） | Monaco 编辑器 + 文件 Tab | 编辑器占位卡片 + "重试"按钮 | 重新加载当前文件（不丢未保存内容，从 stores.editor 读） |
| `SerialBoundary`（串口/分析仪） | xterm.js + 逻辑分析仪 | 终端占位卡片 + "重新连接"按钮 | 新建 xterm 实例 + 重连 WS |
| `InspectorBoundary` | 属性面板 | 面板占位 + "重试" | 重渲染当前选中元件 |
| `LibraryBoundary` | 元件库面板 | 面板占位 + "重试" | 重渲染 catalog |

**错误上报**：所有 Boundary `componentDidCatch` 调用 §1.4 的 `POST /api/ingest/frontend-error`（限频 1 条/10s），payload 加 `boundary` 字段标识出错的 Boundary；`AppRoot` 的上报额外带 `recoverable: false`。

**实现示例（apps/web/src/components/ErrorBoundary.tsx）**：

```tsx
import { Component, type ErrorInfo, type ReactNode } from 'react';
import { reportFrontendError } from '../api/error';

interface Props {
  boundary: string;
  fallback: (error: Error, reset: () => void) => ReactNode;
  children: ReactNode;
}
interface State {
  error: Error | null;
}

export class ErrorBoundary extends Component<Props, State> {
  state: State = { error: null };

  static getDerivedStateFromError(error: Error): State {
    return { error };
  }

  componentDidCatch(error: Error, info: ErrorInfo): void {
    void reportFrontendError({
      msg: error.message,
      stack: error.stack,
      boundary: this.props.boundary,
      componentStack: info.componentStack,
    });
  }

  reset = (): void => this.setState({ error: null });

  render(): ReactNode {
    if (this.state.error) return this.props.fallback(this.state.error, this.reset);
    return this.props.children;
  }
}
```

**使用示例**：

```tsx
<ErrorBoundary
  boundary="canvas"
  fallback={(err, reset) => <CanvasErrorCard error={err} onRetry={reset} />}
>
  <CircuitCanvas />
</ErrorBoundary>
```

**约束**：
- 每个面板的 Boundary 必须提供明确的"重试"路径，不能只显示错误堆栈（用户无操作可恢复等于死锁）；
- `AppRoot` 的 Boundary 之外的 Boundary reset 不能 reset 整个 simStore（避免丢运行中的仿真状态）；只有 `AppRoot` 的 reset 才允许 reload 页面；
- Boundary 不捕获异步错误（Promise rejection / setTimeout 抛错）——这些由 §1.4 的 `window.onerror` + `unhandledrejection` 全局监听上报；
- WS 断线不属于 Boundary 兜底范畴（属于业务降级，由 simStore 状态机处理，见 03-§7.3）。

4. **虚拟 TCP/MQTT 服务**：服务端内置 `net.createServer`（仅 127.0.0.1 + 端口隔离 + 单板连接数限制）；MQTT broker 用 `mqtt` 包（轻量 pub/sub 演示）；服务面板可视化（连接列表 + pub/sub 主题树）；安全边界：`0.0.0.0` 绑定拒绝 + 端口沙箱（不与宿主端口冲突）。
5. **MQTT pub/sub 演示**：示例 `mqtt-hello`（连 broker → 订阅 `esp32/sensor` → 发布温湿度 → 前端服务面板可见消息流）；Golden `expect.mqtt` schema（topic + payload + QoS 断言）+ `assertMqttFlow` helper。
6. **示例 + 测试 + 文档 + 全检查**：mqtt-hello、wifi-connect 两示例 × 双引擎；Golden `expect.mqtt`/`expect.wifi` schema；03-§7.2.2 帧表补 WIFI_TXN/REPLY；05-§2 元件表（无新元件，WLAN 是板载）；06-§3 端口/连接/安全边界；lint/typecheck/test/format 全绿。

**关键决策（阶段 1 拍板）**：

- **D1 虚拟网络隔离策略**：**采纳 127.0.0.1 only + 端口沙箱**（虚拟服务绑定 loopback，外网不可达；端口范围 1883/8080/8883 限定，与宿主冲突时自动 +offset）。备选：netns 命名空间隔离（Linux only + 复杂，弃）、Docker 网络隔离（重量级，弃）。
- **D2 esp_wifi 拦截层**：**采纳 glue 强符号覆盖 esp_wifi_* 函数**（M8 D2 模式扩展，不进 ESP-IDF wifi 栈）；状态转移由宿主模拟（默认 1s CONNECTED + 断网/重连测试用 input.wifi 触发）。备选：LD_PRELOAD 拦截（跨平台差，弃）。
- **D3 MQTT broker 选型**：**采纳内置轻量 broker**（`mqtt` npm 包的 aedes/lambda 实现，单文件）；不引入 mosquitto 外部依赖。备选：mosquitto 子进程（容器化 + 启动开销，弃）。

#### 5.3.1 MicroPython-WASM 定制构建（Dockerfile）

> 在 `tools/mpy-build/` 下维护一份 Dockerfile，用 WSL/Docker 在 Linux 容器内完成 Emscripten 构建，产物 `micropython.wasm` + `micropython.wasm.mjs`（运行时 glue）入库到 `apps/web/src/sim/mpy/`，开发机无需装 Emscripten。

`tools/mpy-build/Dockerfile`：

```dockerfile
FROM emscripten/emsdk:3.1.45

# MicroPython 源码（固定 v1.26.x tag，便于复现）
RUN git clone --depth 1 --branch v1.26.0 https://github.com/micropython/micropython.git /mpy

# 定制 machine 模块：把 apps/web/src/sim/mpy/machine-shim/ 覆盖到 ports/webassembly/modules
COPY machine-shim/ /mpy/ports/webassembly/modules/machine/

WORKDIR /mpy/ports/webassembly

# 编译（产物：build-*/micropython.{wasm,wasm.mjs}）
RUN make clean && make

# 输出
CMD ["sh","-c","mkdir -p /out && cp build-*/micropython.wasm /out/ && cp build-*/micropython.wasm.mjs /out/"]
```

`tools/mpy-build/README.md` 补充使用：

```bash
# 1. 在仓库根执行
docker build -t mpy-wasm-build tools/mpy-build/

# 2. 把产物拷到 apps/web/src/sim/mpy/
docker run --rm -v "$PWD/apps/web/src/sim/mpy:/out" mpy-wasm-build

# 3. 提交 wasm 产物入库（git lfs track *.wasm）
```

`machine-shim/` 目录维护一份 C 模块占位文件（`machine.Pin`/`UART` 注册到 mp_module），具体语义由《03-核心模块详细设计》§3.2 转发表约定。M4 起按 P1 元件表逐个交付 `Pin/UART`，后续 `PWM/ADC/I2C/SPI/RMT`。

## 8. 发布与部署

> 单机定位，不引入 K8s/容器编排；提供两种发布形态，按用户环境选择。

### 8.1 形态一：单机源码 + Node 直接运行（推荐 P1 验收期）

适用：开发者自验、本地部署。前置：本机已装 Node 22.13+、pnpm 11+、Git、（可选）arduino-cli/QEMU。

```bash
git clone <repo> esp32-simulator && cd esp32-simulator
pnpm install
pnpm build              # 构建前端到 apps/web/dist
pnpm --filter server start   # 启动后端，监听 3001；静态托管 apps/web/dist
# 浏览器访问 http://localhost:3001
```

`apps/server` 用 `@fastify/static` 托管 `apps/web/dist`，单端口同时提供 REST/WS/前端页面，避免开发期跨域。

### 8.2 形态二：Docker Compose 一键部署（推荐 P2 终验后对外发布）

适用：交付给非开发用户、CI 自验。前置：本机装 Docker Desktop。

`docker-compose.yml`：

```yaml
services:
  app:
    build: .
    image: esp32-simulator:${VERSION:-latest}
    ports: ["3001:3001"]
    volumes:
      - ./data:/app/data          # SQLite + builds/ + flash/ 持久化
      - ./config:/app/config:ro  # 配置只读
    environment:
      - NODE_ENV=production
    restart: unless-stopped
```

`Dockerfile`（仓库根）：

```dockerfile
FROM node:20-bookworm-slim AS build
WORKDIR /app
RUN corepack enable
COPY pnpm-lock.yaml package.json pnpm-workspace.yaml ./
COPY apps packages config examples tools ./
RUN pnpm install --frozen-lockfile
RUN pnpm build

FROM node:20-bookworm-slim
WORKDIR /app
COPY --from=build /app /app
ENV NODE_ENV=production
EXPOSE 3001
CMD ["node","apps/server/dist/index.js"]
```

> 说明：`arduino-cli` 与 QEMU 工具链镜像内不预装（体积大且与宿主机强相关）；容器启动时 `tools/setup-toolchain.ps1` 等价脚本检测并提示用户挂载工具链目录或安装。`data/` 与 `config/` 走 volume 挂载，镜像本身无状态。

### 8.3 形态三：Windows 服务化（可选，P3 评估）

用 `node-windows` 或 `nssm` 把 `node apps/server/dist/index.js` 注册为 Windows 服务，开机自启；适合"教学机房"场景。P3 评估是否纳入。
