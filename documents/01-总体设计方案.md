## 1. 项目概述

### 1.1 目标
参照 [Wokwi](https://wokwi.com/esp32)，自制一款基于网页的 ESP32 终端模拟器：
- 根据硬件设备**接线布局**（元件放置 + 连线）搭建虚拟电路；
- 在**固件烧录前**在线模拟硬件运行，观察外设行为与串口输出；
- 支持 MicroPython 与 Arduino C++（经编译为固件）两类开发方式。

### 1.2 已确认的核心决策（需求澄清结论）

| 决策项 | 结论 |
|---|---|
| 模拟引擎 | **双引擎分期**：引擎A = 浏览器内 MicroPython-WASM；引擎B = 服务端 QEMU + WebSocket 桥（运行 Arduino/ESP-IDF 编译产物） |
| 外设范围 | **完整套件**：GPIO/LED/按键/电位器、I2C/SPI 传感器、SSD1306 OLED、NeoPixel、WiFi 模拟、多板协作、逻辑分析仪 |
| 架构 | 前后端分离，Node.js 后端 |
| 数据存储 | SQLite 轻量单机库（无用户注册体系） |
| 前端 | React + TypeScript，**双主题可切换**（暗色工程风 / 亮色简洁风） |
| 工程格式 | `diagram.json` 兼容 Wokwi 格式（可导入 Wokwi 工程，加分项） |

### 1.3 非目标（Non-Goals）
- 不做用户注册/登录/多租户云服务（一期不做，列入远期）；
- 不做真实信号级电路仿真（不做 SPICE 模拟电路求解，连线仅表达逻辑拓扑，一期不做，列入远期）；
- 不支持蓝牙模拟（一期不做，列入远期）；
- 不做移动端原生 App（响应式适配网页即可，一期不做，列入远期）。

## 2. 调研结论与选型依据

### 2.1 Wokwi 对标分析
- 电路以声明式 `diagram.json` 描述：`parts[]`（元件实例：id/type/left/top/attrs/rotate）+ `connections[]`（四元组：`[源引脚, 目标引脚, 线色, 布线路径]`，布线路径形如 `["v10","h5","*"]`）。
- 元件库 `wokwi-elements`（Lit Web Components）开源，可评估复用或参照其 SVG 资源自制渲染。
- ESP32 仿真引擎闭源；不同架构使用不同引擎（AVR8js / RP2040js / ESP32 模拟器）。

### 2.2 同类开源项目 Velxio（2026，Espressif 官方博客推荐）
- 前端 React 19 + Vite + TS + Monaco + Zustand，电路画布 + 引脚 overlay + 正交布线；
- ESP32 采用**服务端 QEMU fork（lcgamboa/qemu-8.1.3 picsimlab-esp32 分支）**，WebSocket 桥接前端，后端仅编译与桥接、无状态；
- 支持模拟 WiFi（可真实联网）、I2C、RMT/NeoPixel、LEDC/PWM；
- 结论：**QEMU 放服务端而非浏览器内**，是目前业界唯一被验证的高保真路径。

### 2.3 MicroPython 官方 WebAssembly 移植
- `micropython/webassembly` port 可直接在浏览器运行完整解释器（v1.26+）；
- 需定制构建：注册 `machine` 模块的虚拟外设后端（Pin/UART/I2C/SPI/ADC/PWM），把硬件调用转发到 JS 侧的引脚总线模型；
- 优点：零延迟交互、纯前端运行；限制：仅支持 MicroPython 源码，无法运行编译后的 .bin 固件。

### 2.4 选型结论表

| 模块 | 选型 | 理由 |
|---|---|---|
| 前端框架 | React 18 + TypeScript + Vite | 生态成熟，Konva/Monaco/Zustand 支持完善 |
| 画布 | react-konva（Canvas） | 元件多、连线频繁重绘场景性能优于纯 SVG；元件本体用内嵌 SVG 图像渲染 |
| 代码编辑器 | Monaco Editor | VS Code 同源，支持 Python/C++ 高亮与诊断 |
| 串口终端 | xterm.js | 事实标准，支持 ANSI 颜色与输入回显 |
| 状态管理 | Zustand | 轻量、适合仿真高频事件流 |
| 后端框架 | Node.js 22 + Fastify | 高性能 HTTP + 官方 WebSocket（@fastify/websocket），子进程管理成熟；22 LTS 满足 pnpm 11 的 >=22.13 最低要求 |
| 数据库 | SQLite（better-sqlite3） | 单文件零运维，同步 API 简单可靠 |
| 编译链 | arduino-cli（Arduino C++）；ESP-IDF（进阶）；mpy-cross（可选，MicroPython 字节码） | 与真实烧录流程一致，产物即固件 |
| 引擎B | Espressif QEMU fork（esp-develop，xtensa/riscv32 softmmu）或 lcgamboa fork | 官方维护、支持 ESP32/S3/C3；GPIO/UART 桥接方案有 Velxio 先例 |
| 实时通信 | WebSocket（@fastify/websocket） | 串口流/GPIO 事件/帧缓冲均为双向流 |

### 3.2 引擎统一抽象（关键设计）

两个引擎对上层（画布/终端）暴露同一接口，前端元件不感知引擎差异：

```ts
interface SimulationEngine {
  readonly kind: 'micropython-wasm' | 'qemu-remote';
  load(circuit: CircuitDoc, firmware: FirmwareInput): Promise<void>;
  start(opts?: { speed?: number }): void;
  pause(): void;
  reset(): void;
  dispose(): void;
  // 引擎 → 元件：输出事件
  on(ev: EngineEventBus): void;   // gpio_write | pwm_duty | uart_rx | i2c_txn | spi_txn | framebuffer | log
  // 元件 → 引擎：输入注入
  input(ev: InputEvent): void;    // pin_level | analog_value | sensor_data | uart_tx | key_event
}
```

`CircuitDoc` 即工程内 `diagram.json` 解析结果；`FirmwareInput` 对引擎A是 Python 源文件集合，对引擎B是构建产物（.bin/.elf）。

### 3.3 仿真会话生命周期

```
用户点击“运行”
  ├─ 引擎A：前端本地实例化 MicroPython-WASM → 注入源码 → 绑定 PinBus → 开始执行
  └─ 引擎B：POST /api/build 编译固件 → WS /ws/sim/:sid attach(circuit, firmwareId)
            → QemuManager 拉起 QEMU 进程（挂载 flash 镜像）
            → 建立 GPIO/UART 虚拟外设桥 → 事件流回传前端 PinBus
用户点击“停止/复位” → 信号量广播 → 引擎/进程回收（超时强杀）
```

### 4.3 状态管理（Zustand stores）

- `projectStore`：工程元数据、文件树、脏标记；
- `circuitStore`：parts/connections（单一数据源，画布只读渲染 + action 修改）；
- `simStore`：引擎状态、运行/停止、事件订阅分发；
- `uiStore`：面板折叠、主题、当前选中元件。

### 4.4 画布交互细节
- 元件渲染：每个元件定义 JSON 内含 `renderer` 字段，指向内置 SVG 资源或 Lit 组件封装（评估直接复用 `wokwi-elements`，否则参照其样式自制）；
- 连线：鼠标从引脚拖出 → 实时预览正交折线 → 命中目标引脚吸附落点；支持颜色循环（8 色）与删除；
- 运行态：引脚电平变化时引脚圆点变色（高电平亮/低电平暗），LED/OLED 等输出元件实时刷新；OLED 通过 `framebuffer` 事件重绘；
- 缩放：滚轮缩放（0.25x–4x），空格+拖拽平移，自适应窗口。

#### 5.2.1 REST 统一响应与错误码

**成功响应**（HTTP 2xx，直接返回数据，无 envelope 包裹，简化前端消费）：

```json
// GET /api/projects/abc
{ "id": "abc", "name": "blink", "boardType": "esp32-devkit-c-v4", "engine": "micropython-wasm", ... }
```

**错误响应**（HTTP 4xx/5xx，统一 envelope）：

```json
{
  "error": {
    "code": "PROJECT_NOT_FOUND",
    "message": "Project abc not found",
    "detail": { "projectId": "abc" },
    "traceId": "req_8f3k..."
  }
}
```

**错误码枚举**（与 HTTP 状态对应，前端按 `code` 做精准提示）：

| code | HTTP | 触发场景 |
|---|---|---|
| `BAD_REQUEST` | 400 | 参数缺失/格式错（zod 校验失败） |
| `VALIDATION_FAILED` | 422 | 业务校验失败（如 diagram.json 缺元件） |
| `UNAUTHORIZED` | 401 | 未鉴权（一期单机无用户，预留） |
| `NOT_FOUND` | 404 | 资源不存在（project/build/example） |
| `CONFLICT` | 409 | 并发冲突（如工程被他人改） |
| `PATH_TRAVERSAL` | 400 | 路径穿越检测命中（`../../`） |
| `OVER_LIMIT` | 413 | 超规模上限（元件数/文件大小，见《06-边界说明》§3） |
| `TOOLCHAIN_MISSING` | 503 | 工具链缺失导致无法完成（如未装 QEMU 时调用 build） |
| `BUILD_FAILED` | 422 | 编译失败，`detail.log` 含 arduino-cli 错误 |
| `SESSION_NOT_FOUND` | 404 | WS 会话不存在或已回收 |
| `WS_MSG_INVALID` | 400 | WS 消息未过 zod（经 `error.ack` 回执，见《03-核心模块详细设计》§2.4） |
| `INTERNAL` | 500 | 未捕获异常，`traceId` 用于查日志 |

**约定**：
- `traceId` 由 Fastify 请求钩子注入（`req-<nanoid>`），同步写入响应与 pino 日志（`reqId` 字段），便于关联排查；
- 4xx 错误不进 `error.code` 枚举外的自由字符串，前端 `code` 映射到 i18n key；
- 5xx 错误对前端隐藏内部 stack，仅返 `traceId`。

### 5.3 WebSocket 协议（`/ws/sim/:sessionId`）

消息为 JSON 信封：`{type, payload}`。

**客户端 → 服务端**
| type | payload | 说明 |
|---|---|---|
| `attach` | `{projectId, circuit, firmwareId, boardType}` | 绑定工程并请求启动 QEMU |
| `input.pin` | `{partId, pin, level}` | 按键/开关状态 |
| `input.analog` | `{partId, pin, value}` | 电位器/传感器值注入 |
| `input.uart` | `{bytes}` | 终端输入发送 |
| `ctrl` | `start/pause/reset/stop` | 运行控制 |

**服务端 → 客户端**
| type | payload | 说明 |
|---|---|---|
| `state` | `{status, error?}` | 会话状态机 |
| `gpio.write` | `{pin, level}` | GPIO 输出 |
| `pwm.duty` | `{pin, duty, freq}` | PWM 输出 |
| `uart.rx` | `{bytes}` | 串口输出（终端显示） |
| `i2c.txn` | `{addr, dir, data}` | I2C 事务（传感器/OLED 消费） |
| `spi.txn` | `{cs, data}` | SPI 事务 |
| `fb.update` | `{partId, data}` | OLED 帧缓冲增量更新 |
| `log` | `{level, text}` | QEMU/系统日志 |

### 5.4 QEMU 集成方案（引擎B核心）
- 二进制：Espressif 官方 QEMU fork 预编译版（`qemu-system-xtensa` / `qemu-system-riscv32`，esp-develop 9.x）；
- 启动参数：`-machine esp32 -drive file=flash.img,if=mtd -serial tcp:… -monitor none`，每会话独立工作目录与端口；
- **外设桥接**：
  - UART：`-serial` 直连 TCP → WS `uart.rx/tx` 透传（零改造）；
  - GPIO/PWM：采用 lcgamboa fork（picsimlab-esp32 分支）提供的 GPIO 导出能力，或按 Velxio 方案定制轻量虚拟外设设备模型，将 GPIO 翻转转译为 WS 事件；
  - I2C/SPI：虚拟总线设备（一期先覆盖 SSD1306 与常用传感器地址）；
  - WiFi：一期采用“伪 WiFi”语义模拟（`esp_wifi` 调用返回成功 + 内置虚拟 TCP/MQTT 服务端）；
- 生命周期：会话关闭/超时（默认 30 分钟无活动）→ 优雅退出 → 超时强杀 → 清理 flash 工作目录。

### 5.5 构建服务
- **arduino-cli**：预装 esp32 板卡支持包；按工程文件生成 sketch 编译；产物合并为 flash 镜像（esptool merge_bin）；
- **ESP-IDF**（进阶，可延后）：容器化工具链或本机安装检测；
- 编译任务队列：并发上限 2，任务落库（builds 表），前端轮询或 WS 推送进度；
- 安全：编译输入仅允许工程文件沙箱目录，禁止任意路径；超时 5 分钟终止。

#### 5.5.1 Flash 镜像偏移布局（N18）

> §5.5 提 esptool `merge_bin` 生成 flash.img；N18 给出实际偏移布局，让 BuildService 与 QemuManager 都能正确读写。

**ESP32 标准分区偏移**（与 esptool/QEMU 兼容）：

| 分区 | 偏移 | 默认大小 | 来源 |
|---|---|---|---|
| bootloader | 0x1000 | 32KB（0x8000） | arduino-cli 编译产物 `sketch.ino.bootloader.bin` |
| partition_table | 0x8000 | 4KB（0x1000） | `sketch.ino.partitions.bin`（默认 `default.csv`） |
| application | 0x10000 | ≤1.3MB（受分区表约束） | `sketch.ino.bin`（主固件） |
| (可选) nvs | 0x6000 | 4KB | 用户数据，一期不写入 |

**merge_bin 调用**（BuildService 内部）：

```ts
// args 数组化（不 shell 拼接）
const args = [
  '--chip', 'esp32', '--merge-output',
  '-o', `${workdir}/flash.img`,
  '0x1000', `${sketchDir}/sketch.ino.bootloader.bin`,
  '0x8000', `${sketchDir}/sketch.ino.partitions.bin`,
  '0x10000', `${sketchDir}/sketch.ino.bin`,
];
await execa('esptool', args, { cwd: workdir, timeout: 30000 });
// 产物：data/builds/<buildId>/flash.img，约 1.5MB（最小可用镜像）
```

**QEMU 挂载**（03-§7.2.1 `-drive file=flash.img,if=mtd`）：
- QEMU `-drive if=mtd` 把 flash.img 当 SPI flash 设备挂载，按 ESP32 启动逻辑从 0x1000 读 bootloader → 跳到 0x10000 执行 app；
- flash.img 必须 ≥1.5MB（覆盖到 0x10000 + app_size）；`merge_bin` 默认补 0x00 填充到对齐；
- ESP32-S3 / C3 偏移相同（bootloader 0x1000 / partition 0x8000 / app 0x10000），但 `-chip esp32s3` 或 `esp32c3`。

**ESP-IDF 场景（P3 评估）**：偏移由 `partitions.csv` 决定，不固定；esptool merge_bin 仍用同一参数模式，但要读 partitions.csv 提取实际偏移，不能硬编码。

> 不引入 `esptool.py image_info` 验证：QEMU 启动失败会直接 stderr 报错，BuildService 捕获后转 `build.progress` `failed`；前端不需要单独验证镜像。

### 6.1 Migration 机制（N15）

> better-sqlite3 无内置 ORM/migration runner；自研轻量方案，避免引入 knex/drizzle（单机定位不值得）。

**runner**：`apps/server/src/db/migrator.ts`，启动时调用 `runMigrations(db)`：

```ts
// 伪代码
function runMigrations(db: Database) {
  db.exec(`CREATE TABLE IF NOT EXISTS _migrations (
    id          INTEGER PRIMARY KEY,           -- 递增编号
    filename    TEXT NOT NULL UNIQUE,         -- '0001_init.sql'
    applied_at  INTEGER NOT NULL              -- 应用时间戳
  )`);

  const applied = new Set(db.prepare('SELECT filename FROM _migrations').all().map(r => r.filename));
  const files = fs.readdirSync('apps/server/src/db/migrations')
                   .filter(f => f.endsWith('.sql'))
                   .sort();
  for (const f of files) {
    if (applied.has(f)) continue;
    const sql = fs.readFileSync(`apps/server/src/db/migrations/${f}`, 'utf8');
    db.transaction(() => {
      db.exec(sql);
      db.prepare('INSERT INTO _migrations (filename, applied_at) VALUES (?, ?)').run(f, Date.now());
    })();
    log.info({ module: 'db', msg: `migration applied: ${f}` });
  }
}
```

**文件命名**：`<编号>_<主题>.sql`，按字典序应用（编号严格递增，4 位起）：

```
apps/server/src/db/migrations/
├── 0001_init.sql              # 初始 schema（§6 所有 CREATE TABLE）
├── 0002_add_thumbnail.sql     # 后续演进示例（在 projects 加 thumbnail 列）
├── 0003_builds_pinned.sql     # 加 pinned/started_at 列
└── ...
```

**约束**：
- 每个 migration **不可逆**（不写 down 脚本；单机定位，回滚靠 git revert + 删 `data/simulator.db` 重建）；
- 每个 migration 必须包在 transaction 里（失败回滚）；
- 不能修改已应用的 migration 文件（修改后 _migrations 表已记录 filename，不会重跑）；要改用新编号追加；
- 测试期重置 db：`rm data/simulator.db && pnpm --filter server dev` 自动从 0001 跑到最新。

**种子数据**：`apps/server/src/db/seed.ts`，仅开发期运行（`pnpm --filter server seed`），写入示例工程 + 元件 catalog；生产部署不自动跑（用户从 `/api/examples` 拉取内置示例）。

#### 7.4.1 `diagram.json` ↔ `CircuitDoc` 映射（N4）

> §7.4 是 Wokwi 兼容格式（用于工程文件、导入/导出、JSON 源码视图）；《03-核心模块详细设计》§2.1 `CircuitDoc` 是内部模型（前端 store + WS 协议）。M3 Wokwi 导入验收前必须明确映射，避免字段不对齐卡死。

**字段映射表**：

| `diagram.json`（Wokwi 格式） | `CircuitDoc`（内部模型） | 转换说明 |
|---|---|---|
| `version: 1` | `formatVersion: 1` | 改名（Wokwi `version` 是 schema 版本；CircuitDoc `formatVersion` 含义一致，命名对齐本仓库风格） |
| `author: "me"` | （丢弃） | 单机无用户体系，CircuitDoc 不保留；导入时记入 `projects.description`（"原作: me"） |
| `editor: "esp32-simulator"` | （丢弃） | 编辑器标识不进运行模型；导出时写当前版本号 |
| `parts: [{id, type, left, top, attrs}]` | `parts: PartInstance[]` | 字段对齐，加 `rotate: 0`（diagram.json 无 rotate 时默认 0），`attrs` 缺省时为 `{}` |
| `connections: [[src, tgt, color, path]]` | `connections: Connection[]` | 元组转对象：`{id: nanoid(), source: src, target: tgt, color, path: WireSegment[]}` |
| `serialMonitor: {baudrate}` | `serialMonitor: {baudrate}` | 直传 |
| （无） | `boardType: "board-esp32-devkit-c-v4"` | 从 `parts[0].type` 提取（约定 parts[0] 永远是板卡） |

**`boardType` 前缀统一规则**（解决 03-§2.1 注释 `esp32-...` 与 01/05 `board-esp32-...` 不一）：

- **板卡 type**：统一带 `board-` 前缀，如 `board-esp32-devkit-c-v4`、`board-esp32-s3-devkitc-1`、`board-esp32-c3-devkitm-1`；
- **元件 type**：不带 `board-` 前缀，如 `wokwi-led`、`wokwi-pushbutton`；
- **CircuitDoc.boardType**：存板卡 type（即 `board-esp32-devkit-c-v4`），与 `parts[0].type` 一致；
- **PinRef**：板卡引脚 PinRef = `${partId}:${pinName}`（如 `esp:GPIO4`），不带 type 前缀（partId 已唯一标识）；
- 03-§2.1 注释 `boardType: "esp32-devkit-c-v4"` 是历史笔误，**以本节为准**：板卡 type 全部带 `board-` 前缀。

**Wokwi `connections` 路径语义**（`v`/`h`/`*` + 长度）→ `WireSegment[]`：

| Wokwi | WireSegment | 说明 |
|---|---|---|
| `"v10"` | `{dir: 'v', len: 10}` | 垂直 10 单位（向下） |
| `"h-5"` | `{dir: 'h', len: -5}` | 水平 -5 单位（向左，长度带符号） |
| `"*"` | `{dir: '*', len: 0}` | 自动正交布线（M2 简化版：先 v 后 h） |
| `[]` | `[]` | 空路径，等价于 `[{dir:'*', len:0}]` |

> 转换实现：`apps/web/src/circuit/io/wokwi-import.ts`（导入）+ `wokwi-export.ts`（导出），M3 实现；单元测试用 §7.4 示例 JSON 做 round-trip 验证。

## 9. 分期规划（与实施方案衔接）

> 评审结论（已确认）：**双引擎并行**——自 M4 起，每个能力里程碑内引擎A与引擎B能力对齐交付，同一 Golden 剧本在两引擎下均需通过（引擎B按实际支持度标注例外）。详见《02-实施方案》§4。

- **P1（基础闭环，M1–M6）**：脚手架与协议、画布与连线、工程管理与元件配置落地、**双引擎·串口级闭环**（引擎A MicroPython-WASM / 引擎B arduino-cli 编译 + QEMU UART）、**双引擎·GPIO 输入输出闭环**（PinBus + QEMU GPIO 桥）、P1 终验；
- **P2（完整套件，M7–M12）**：PWM/ADC（双引擎）、I2C/SPI 总线与传感器（双引擎）、SSD1306/NeoPixel（双引擎）、WiFi 语义模拟（双引擎）、逻辑分析仪（两引擎共用）、P2 终验；
- **P3（进阶，按需启动）**：ESP-IDF 工具链、多板协作、Wokwi 工程导入完善、内置示例库扩充。

## 10. 关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| MicroPython-WASM 定制构建（machine 模块虚拟化）工作量超预期 | 引擎A延期 | 先跑通官方 wasm port 基线，machine shim 按外设逐个交付；P1 只做 Pin/UART |
| QEMU GPIO/I2C 桥接需要定制设备模型，C 侧开发门槛高 | 引擎B延期 | P2 优先 UART/WiFi（原生支持）演示 Arduino 价值；GPIO 采用 lcgamboa fork 现成能力；必要时压缩为“串口+WiFi”先行 |
| 画布连线布线算法细节多（正交避障） | 交互体验差 | P1 实现简化正交布线（手动编辑路径），P2 增加自动避障 |
| 浏览器端高频事件（逻辑分析仪）卡顿 | P2 性能 | 事件环形缓冲 + 采样率上限 + requestAnimationFrame 批量绘制 |
| Windows 下 QEMU 子进程/端口管理 | 部署复杂度 | 后端统一进程池 + 端口分配器，Docker 化作为可选发布形态 |
