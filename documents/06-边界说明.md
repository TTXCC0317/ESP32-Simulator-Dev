## 1. 功能边界总表

### 1.2 范围外（Out of Scope，远期评估）

| 能力 | 不做的原因 |
|---|---|
| 用户注册/登录/云同步 | 轻量单机定位（SQLite 无用户体系） |

| 真实外网联网 | 安全与合规风险，仅虚拟网络 |
| 移动端 App | 响应式网页即可 |
| 多人实时协作编辑 | 单机定位 |

## 2. 模拟精度边界（重要声明）

模拟器目标是**固件逻辑行为验证**，不承诺以下真实硬件特性：

| 维度 | 模拟程度 | 边界说明 |
|---|---|---|
| CPU 时序 | 近似 | 引擎A 受浏览器调度影响，非实时；Golden 测试容差 ±100ms。不承诺微秒级精确时序 |
| 外设寄存器 | 引擎B 完整 / 引擎A shim | 引擎A 的 `machine.*` 为语义等价实现，不模拟寄存器细节（ESP32 特定寄存器位操作不可用） |
| 电气特性 | 不模拟 | 无上拉/下拉隐式行为之外的分压、漏电流、功耗计算；电阻为逻辑直通（《05-元件清单》§1.5） |
| 中断延迟 | 近似 | 不保证真实中断响应延迟 |
| RTC 深度睡眠 | 语义模拟 | `deepsleep` 立即返回并触发复位事件，不模拟真实唤醒时序 |
| Flash 布局 | 引擎B 真实 / 引擎A 虚拟文件 | 引擎A 提供内存虚拟文件系统 |
| WiFi 时延/丢包 | 不模拟 | 虚拟网络零丢包、恒定时延 |
| ADC 精度 | 注入值直读 | 不模拟量化噪声/非线性 |
| 浮点/双核 | 引擎B 支持 | 引擎A 与浏览器 WASM 能力一致 |

### 3.1 逻辑分析仪采样率与通道上限（N21）

M11 逻辑分析仪是 PinBus 事件捕获，不是真实硬件 ADC，受限于浏览器事件循环与 WASM 调度，需要明确以下边界，避免用户期待示波器级精度：

| 项 | 上限 | 超限行为 |
|---|---|---|
| 通道数 | 8 | 第 9 通道加入时拒绝并提示"已达通道上限"，需先关闭现有通道 |
| 采样率 | 1 MHz（每通道） | 用户设高于 1 MHz 时强制降为 1 MHz 并 `log.warn`；高于 1 MHz 的真实信号在浏览器侧本就不可分辨 |
| 单次捕获时长 | 5 秒（连续采集） | 超时自动停止采集并保存缓冲；用户可在 UI 中继续重启 |
| 总采样点 | 100 万（8 通道合计） | 触发后丢弃最旧采样点（环形缓冲），UI 标注"已溢出" |
| 事件缓冲 | 10 万事件（环形，与 §3 表对齐） | 同上，丢弃最旧事件并标注 |
| 实时绘制帧率 | 30 fps（自动降采样） | 超过窗口可视像素数时按"N 个事件聚合为 1 像素"策略降采样；用户可缩放波形后查看原始采样点 |
| 游标读数精度 | 1 µs | 受 1 MHz 采样率限制，更小分辨率无意义 |

**采样率分档**：UI 提供 100 Hz / 1 kHz / 10 kHz / 100 kHz / 1 MHz 五档可选；低于 PinBus 事件实际频率时分档即降采样（按 N 事件取最新值），用户应感知到"采样率低于事件频率时波形可能丢失边沿"。

**通道配置**：用户可在逻辑分析仪面板勾选要采集的 PinRef（最多 8 个），未配置的 PinRef 不计入缓冲；切换通道配置会清空当前缓冲（避免混通道数据）。

**降采样策略**（实时绘制时）：
- 1 个屏幕像素覆盖 N 个采样点时（N > 1），按以下规则聚合：
  - 数字信号（GPIO）：取该像素窗口内的"电平翻转次数 + 起止电平"，绘制为该像素内的最小折线；
  - 模拟信号（ADC/PWM duty）：取该像素窗口内的 min/max，绘制为该像素内的填充矩形（"包络"模式）；
- 用户缩放到 1 像素 ≤ 1 采样点时，恢复单点绘制。

**与 PinBus 的协议**：
- PinBus `subscribe(pinRef, callback)` 注册采集回调（M5 已实现，03-§4.1）；
- 逻辑分析仪为每个通道注册一个 callback，事件进入环形缓冲（IndexedDB 不持久化，仅会话内存）；
- 单会话最多 8 个 subscription，超出按"先注册者胜"原则拒绝新通道。

**与 §2 模拟精度边界的关系**：
- §2 表中"CPU 时序 近似 Golden 容差 ±100ms"决定逻辑分析仪不承诺微秒级真实时序；
- 1 MHz 采样率是浏览器定时器精度（`setTimeout` 最小 4ms，`performance.now` 1µs 精度）的折中值；
- 引擎B（QEMU）的 GPIO 桥事件频率实际可达 ~100 kHz，1 MHz 上限足够覆盖；引擎A（WASM）的 PinBus 事件频率受 16ms 批量聚合限制，最高有效频率约 60 Hz——引擎A 下逻辑分析仪主要观察慢速信号（按键、I2C 事务），不适用于 kHz 级 PWM 调试。

## 4. 资源与生命周期边界

| 项 | 规则 |
|---|---|
| QEMU 会话超时 | 空闲 30 分钟自动回收；断开 WS 后保留 60 秒供重连，超时回收 |
| QEMU 异常退出 | state=error + 退出码与 stderr 尾部日志回传；进程表保证无孤儿进程（启动记录 pid，回收时校验） |
| 磁盘配额 | builds/ 目录总量 2 GB，超限清理最旧构建产物（清理前提示用户，详见下方说明） |
| flash 临时目录 | 会话结束即删除；异常残留由后端启动时扫描清理（>24h 的会话目录） |
| 浏览器内存 | 引擎A 单会话 WASM 内存上限 256 MB（超限提示并停止） |
| 页面关闭 | 引擎A 实例随页面释放；引擎B 会话走超时回收 |

#### 4.1 磁盘配额超限的清理策略（F3）

`builds/` 目录总量超 2GB（可配 `builds.quotaMb`，见 §01 §7.6）时的处理流程：

1. **被动触发**：每次 `BuildService.submit` 成功落盘新产物后，扫一遍 `data/builds/` 总量；超限时进入清理；
2. **清理顺序**：按 `builds.finished_at` 升序，从最旧开始删除，直到剩余量降到 `quotaMb × 0.9`（保留 10% 余量，避免频繁触发）；
3. **用户提示**：清理前在 WS 推送 `log.warn` "磁盘配额超限，清理最旧 N 个构建产物"；同时 REST `GET /api/builds?status=success` 返回的列表里被清理的 build 标 `artifactMissing: true`；
4. **不弹模态**：单机定位，构建产物多用于即时烧录，删了就删了；用户若需保留某 build，可在工程详情页"固定构建"（在 builds 表加 `pinned` 字段，清理时跳过）；
5. **不阻塞新编译**：清理与新编译异步并行（清理在 worker thread 跑，主线程不卡）。

| 项 | 规则 |

| 静态资源隔离 | L4 E2E：浏览器访问 `http://localhost:3001/api/projects/../data/simulator.db`，断言 404 而非下载；访问 `http://localhost:3001/data/builds/`，断言 404 | Playwright |

## 7. 错误边界与降级策略

| 场景 | 行为 |
|---|---|
| 工具链缺失 | 引擎B/编译入口置灰 + 引导文档链接；引擎A 完整可用 |
| 引擎A 运行时崩溃（WASM 异常） | 捕获 → 错误面板展示 traceback → 会话回到 idle，画布数据不受影响 |
| 画布 JSON 损坏 | 进入"只读修复模式"，展示原始 JSON 与错误位置，允许手动修复或回退最近 5 次自动快照 |
| SQLite 打开失败 | 后端启动失败并给出明确原因（文件占用/权限） |
| WS 断线 | 前端自动重连（指数退避 ≤5 次，间隔 1/2/4/8/16s，详见下方说明），会话若已被回收则提示重新 attach |

#### 7.1 WS 重连指数退避具体间隔（F1）

断线后前端按以下间隔序列重试，5 次失败后停止并提示：

| 重试次数 | 间隔 | 行为 |
|---|---|---|
| 1 | 1s | 静默重连 |
| 2 | 2s | 静默重连 |
| 3 | 4s | 顶栏状态灯闪黄 + "重连中…" |
| 4 | 8s | 同上 |
| 5 | 16s | 同上 |
| 失败后 | — | 状态灯转红，提示"会话已断开，点击重试或新建会话" |

- 间隔用 `setTimeout` 实现（不是 `setInterval`，避免叠加）；
- 用户可手动点"立即重连"按钮跳过等待；
- 后端在 `reconnectGraceMs`（60s，见 §01 §7.6 配置）内保留会话，重连 `attach` 成功后 `state=running`；超 60s 会话被回收，重连 attach 返回 `SESSION_NOT_FOUND`，前端提示"重新 attach"；
- 不引入 jitter：单机定位，4 并发会话场景下退避叠加概率低；P3 升级到多租户再评估加 jitter。

#### 7.1.1 WS 心跳与空闲检测（N20）

§7.1 处理"已经断线"场景，本节处理"还在连但要确认是否真的活着"。WS 协议本身没有 TCP 层 keep-alive 的可靠信号（浏览器 `WebSocket` 不暴露 `TCP_KEEPIDLE`），故应用层必须自实现心跳，否则会话半死时（如笔记本休眠、网络切换）后端无法及时回收资源。

**心跳协议**：

| 角色 | 行为 |
|---|---|
| 前端 | 每 15s（默认 `ws.heartbeatIntervalMs`，见 §01 §7.6）发 `ClientMsg: { type: 'ping', ts: Date.now() }`；收到 `pong` 后更新 `lastPongTs` |
| 后端 | 收到 `ping` 立即回 `ServerMsg: { type: 'pong', ts: Date.now() }`；同时更新 `lastClientTs` |
| 后端独立定时器 | 每 5s 扫描在线 WS 会话，对 `now - lastClientTs > 60s` 的会话视为"客户端无心跳"，主动 close WS 并触发 §7.1 重连流程 |
| 前端独立定时器 | 每 5s 检查 `now - lastPongTs > 45s`（容忍 3 次心跳丢失），主动 close WS 并触发 §7.1 重连流程 |

**参数与配置**：

| 参数 | 默认值 | 配置项 | 说明 |
|---|---|---|---|
| 前端心跳发送间隔 | 15s | `ws.heartbeatIntervalMs` | 太短增加 CPU/网络负担，太长半死检测延迟；15s 是浏览器后台 throttle（1Hz）的下界附近 |
| 前端失活判定 | 45s | `ws.heartbeatLossThresholdMs` | 容忍 3 次 ping 丢失（3 × 15s = 45s）后判定连接已死 |
| 后端失活判定 | 60s | `ws.sessionIdleTimeoutMs` | 略长于前端失活判定，避免误杀存活会话 |
| 后端会话总超时 | 30 min | `ws.sessionMaxLifetimeMs`（见 §4 QEMU 会话超时对齐） | 不论心跳是否健康，30 min 强制结束会话（与 §4 资源边界对齐） |

**zod schema（packages/shared/src/ws-protocol.ts）**：

```ts
export const pingSchema = z.object({
  type: z.literal('ping'),
  ts: z.number().int().nonnegative(),
});
export const pongSchema = z.object({
  type: z.literal('pong'),
  ts: z.number().int().nonnegative(),
});
```

**降级与边界**：
- 心跳消息不计入 §6 单会话 200 msg/s 速率上限（心跳 1/15s 远低于此）；
- 心跳失败 ≠ WS close：心跳超时由前端主动 close 触发重连，而不是等服务端 close（避免等 TCP RST 浪费时间）；
- 引擎A（MicroPython-WASM）不依赖 WS 心跳——前端 Worker 与主线程纯 postMessage 通信，无网络层；N20 仅适用于引擎B（QEMU+WS 桥）链路；
- 浏览器后台 tab（`document.hidden`）下心跳仍发送（`setTimeout` 在 background tab 会被 throttle 至 1Hz，但 15s 远大于 1s，不受影响）；
- 用户手动点"断开"按钮时不触发心跳超时（先主动 close 再停止心跳定时器）。

**与 §4 QEMU 会话超时的衔接**：
- §4 "空闲 30 分钟自动回收"以 WS 心跳判定为准：60s 无心跳视为空闲开始计时，30 分钟到则强制回收；
- §4 "断开 WS 后保留 60 秒供重连"的 60s 即 §7.1 `reconnectGraceMs`，与心跳超时独立——心跳超时是"还在连但已死"，grace 期是"已 close 但允许复活"。

**测试用例（L3，M4 起）**：
- 心跳 ping/pong 往返用例（发 ping 断言收到 pong）；
- 心跳超时用例：mock 客户端不发 ping 60s 后，断言后端 close 并 `state=error`；
- 心跳恢复用例：客户端慢发 ping（间隔 30s），断言后端不断开；
- 失活恢复用例：客户端 60s 不发心跳后，主动恢复心跳发送，断言后端不立即 close（在失活判定前恢复）。


#### 7.2 画布自动快照存储位置与回退（F2）

- **触发时机**：用户每次 `circuitStore.replaceDoc`/保存（PUT）成功后，前端把上一次成功保存的 `CircuitDoc` 快照写入 IndexedDB `project:<id>:snapshot:<n>`（环形 5 个槽）；
- **存储位置**：IndexedDB（不存后端，避免污染 SQLite 权威数据；快照仅为修复辅助）；
- **回退流程**：JSON 损坏时只读修复模式展示"最近 5 次自动快照"列表（时间戳 + 元件数），用户选择某条后 `circuitStore.replaceDoc(snapshot)` 覆盖当前损坏 JSON，并 PUT 后端；
- **TTL**：快照保留 24h，超时清理（避免 IndexedDB 累积）；
- **不存档历史版本**：单机定位，不做完整版本管理；P3 评估是否引入工程版本树。
